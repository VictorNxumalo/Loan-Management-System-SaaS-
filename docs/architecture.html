LMS — Loan Management System
High-Level Architecture & Tech Stack

A triple-portal, multi-tenant lending SaaS: lenders run an organisation workspace, borrowers use a self-service portal, and platform operators manage cross-tenant support and compliance. Money flows through internal wallets (demo/staging) with optional Stitch bank disbursements; repayments via wallet or external bank proof. NCA loan agreements gate disbursement. This document is the single-page reference for structure, technology choices, and security.

Monorepo · pnpm workspaces Frontend · Next.js 14 Backend · NestJS 11 Database · PostgreSQL (Supabase) + Prisma 6 Queue · BullMQ + Redis Tenancy · Postgres RLS Deploy · Vercel + Render + Supabase

1System Overview

The LMS is an API-first, multi-tenant SaaS. Every lender is an Organisation (tenant); every piece of tenant data carries an org_id and is isolated at the database layer with Row Level Security. Borrowers are platform-level users who connect to one or more lender organisations.

Portal Lender Workspace

  • Portfolio dashboard & metrics
  • Borrower CRM (CRUD + platform search)
  • Loan origination, schedules, repayments
  • Application review (approve / reject / checklist)
  • Loan agreement generation & disburse (sign-gated)
  • Org wallet, payment submission review
  • Team management, audit log, billing, reports

Portal Borrower Portal

  • Onboarding & profile
  • Lender marketplace (browse / connect)
  • Accept lender invites
  • Submit & track loan applications
  • Sign NCA loan agreements electronically
  • View active loans, pay from wallet, report bank payments
  • Borrower wallet & profile KYC

Core Platform Services

  • JWT auth + Google OAuth · profile KYC
  • Financial engine + NCA rate cap
  • Notifications (in-app SSE + email + SMS)
  • Stripe SaaS billing + trial enforcement
  • Wallets, payment submissions, Stitch (optional)
  • Support tickets + platform compliance console
  • Immutable audit trail

Portal Platform Operator

  • /platform — cross-tenant overview
  • Support ticket queue (lender + borrower issues)
  • Lender compliance verification (UNVERIFIED → VERIFIED → REGISTERED)
  • Access via PLATFORM_ADMIN_EMAILS allowlist

Hybrid model: NextAuth manages the browser session; the NestJS API issues and verifies its own JWTs. Supabase Auth is not used.

NextAuth (web)

③ issues tokens

24-hour expiry · Bearer header on every API call

11Multi-Tenancy & Row Level Security

Tenant isolation is enforced in the database itself, not just in application queries. This is the system's most important security property.

Request-scoped Prisma interactive transaction (DIRECT_URL)
PrismaService.setSessionContext() runs set_config('app.current_org_id', …) · app.current_user_id · app.auth_lookup · app.token_lookup
every query in the transaction
PostgreSQL RLS policies
Tenant tables filtered by org_id = current_setting('app.current_org_id'); borrower-side policies grant cross-tenant reads only via BorrowerLenderLink connections
Even a buggy or missing WHERE clause cannot leak another tenant's rows.
  • Two connection strings: DATABASE_URL (Supavisor transaction pooler, port 6543, pgbouncer=true) for general traffic; DIRECT_URL (session pooler, port 5432) for migrations and RLS interactive transactions.
  • Cross-tenant policies are explicit: dedicated migrations grant borrowers read access to connected orgs, lenders read access to connected borrower profiles, and public marketplace listing reads.
  • Tested: dedicated tenant-isolation integration tests in the API suite.

13Cross-Cutting Concerns

Money Financial integrity

  • All amounts stored and transmitted as integer cents
  • @lms/utils/finance: Decimal.js schedule generation — flat & reducing-balance interest, weekly/biweekly/monthly periods
  • @lms/utils/nca-rates: NCA max rate (repo × 2.2) + 20%; enforced on approve/create/update
  • loan-agreement-template: HTML agreement generation + signature append
  • loan-balance: outstanding balance + computeDaysOverdue
  • Schedules immutable once generated; repayments insert-only

Audit Compliance trail

  • Immutable audit_logs with before/after JSON snapshots
  • Written inside the same org-scoped transaction as the business change
  • Covers borrowers, loans, applications, agreements, documents, team, connections
  • Audit failures are logged but never break the business operation

Contract Validation strategy

  • One Zod schema per operation in @lms/types
  • Frontend: react-hook-form resolvers
  • Backend: ZodValidationPipe on every endpoint
  • API env itself validated with Zod at boot (config/)

Files Document handling

  • Private Supabase bucket lms-documents, org-scoped paths
  • Browser uploads directly via short-lived signed URLs (API never proxies bytes)
  • Metadata in documents table; PDF/JPEG/PNG, 10 MB cap
