1. Project Overview

1.1 What We Are Building

We are building a multi-tenant, cloud-hosted Software-as-a-Service (SaaS) web application called LMS — Loan Management System. The platform is designed for lenders: individuals and organisations that loan money to other people (borrowers) and need a digital tool to manage, track, and consolidate all of their lending activity in one place.

This is NOT a bank or a licensed financial institution. LMS is a management and record-keeping tool — a productivity platform for lenders, comparable to how a CRM is a tool for salespeople. The platform does not hold funds, process payments, or act as a financial intermediary.

1.2 Target Users

The platform serves two distinct user roles within each tenant organisation:

Role

Who They Are

What They Do in LMS

Admin / Owner

The lender — the person or organisation that signs up and owns the account

Full access: manage borrowers, create loans, configure settings, manage team members, view all reports, manage billing

Loan Officer

A staff member or agent added by the Admin

Operational access: create borrowers, create and manage loans, record repayments, view assigned portfolios

Read-Only Viewer

Accountant, auditor, or silent partner added by Admin

View-only access: read all data, export reports, no ability to create or modify records

1.3 Core Problem Being Solved

Informal and semi-formal lenders currently track loans using a combination of paper ledgers, WhatsApp messages, Excel spreadsheets, and memory. This creates the following problems:

No centralised view of total outstanding portfolio or cash flow

No automated tracking of who is overdue and by how much

No audit trail — disputes arise when records are lost or altered

No way to generate proper loan agreements or statements for borrowers

Difficult to scale beyond a handful of active loans

LMS solves all of these by providing a structured, audited, always-available digital platform.

2. Product Requirements

2.1 MVP Feature Set (Phase 1)

The MVP must be fully functional before any Phase 2 features are considered. Every feature below is required for launch.

2.1.1 Authentication & Onboarding

Email + password registration with email verification

OAuth sign-in via Google

Tenant (organisation) created automatically on first sign-up

Guided onboarding wizard: organisation name, logo upload, default currency, default interest calculation method

Password reset via email

Session management with refresh tokens and secure logout

2.1.2 Borrower Management

Create, read, update, soft-delete borrower profiles

Required fields: full name, ID number (or passport), phone number, email (optional)

Optional fields: physical address, employer name, monthly income

Document uploads per borrower: ID copy, proof of income, proof of address (stored in S3/cloud)

Borrower search and filter by name, ID number, status

Borrower detail page showing full loan history, total borrowed, total repaid, outstanding balance

2.1.3 Loan Management

Create a loan linked to a borrower

Required loan fields: principal amount, interest rate (%), interest type (flat rate or reducing balance), loan term (months or weeks), start date, repayment frequency (weekly / bi-weekly / monthly)

System auto-generates repayment schedule (amortisation table) on creation

Loan statuses: Draft, Active, In Arrears, Completed, Written Off

Edit loan terms only while status is Draft

View full amortisation schedule per loan

Record manual repayments against a loan (amount, date, note)

System auto-calculates remaining balance, interest paid, principal paid after each repayment

Support for partial repayments and lump-sum early repayments

Soft-delete / write-off with mandatory reason

2.1.4 Financial Calculations

All monetary calculations MUST use a decimal library (decimal.js or equivalent). Never use native JavaScript floating-point arithmetic for financial figures. Store all money values as integers in cents in the database.

Flat rate interest: interest = principal × rate × term; repayment = (principal + total interest) / number of periods

Reducing balance interest: standard amortisation formula recalculates interest on outstanding principal each period

Late fee calculation: configurable per-loan or system-default (flat fee or % of overdue amount per day/week)

All calculations must be unit-tested with known expected outputs before connecting to the UI

2.1.5 Dashboard & Reporting

Main dashboard KPIs: total active loans, total portfolio value (outstanding principal), total repayments collected this month, number of loans in arrears, arrears rate (%)

Upcoming repayments widget: next 7 days and next 30 days

Overdue loans list: sorted by days overdue descending

Loan portfolio report: all active loans with balances (exportable to CSV / PDF)

Repayment history report: all repayments in a date range (exportable)

Borrower statement: per-borrower PDF showing all loans and repayments

2.1.6 Notifications

Email reminders to borrowers 3 days before repayment due date (configurable)

Email alert to lender when a repayment becomes overdue (1 day after due date)

In-app notification bell for: new overdue loans, system alerts

SMS notifications via configurable provider (Twilio or Africa's Talking) — optional per tenant, on by default if SMS credentials are configured

2.1.7 Team Management (Admin Only)

Invite team members by email

Assign roles: Loan Officer or Read-Only Viewer

Revoke access / deactivate team member

Audit log: every data change logged with user, timestamp, and before/after values — immutable

2.1.8 Billing & Subscription

Stripe-powered subscription management

Starter plan: up to 50 active loans, 1 user

Pro plan: up to 500 active loans, up to 5 users

Business plan: unlimited loans, up to 20 users, custom branding

14-day free trial, no credit card required on signup

In-app billing portal (Stripe Customer Portal) for plan changes, invoice downloads

Graceful degradation when trial expires: read-only mode until plan is activated

3. Technical Architecture

3.1 Architecture Pattern

The application follows a standard three-tier web architecture: a React single-page application (SPA) frontend served via a CDN, a RESTful API backend running on Node.js, and a managed PostgreSQL database. The frontend and backend are deployed independently.

Multi-tenancy model: Shared database, shared schema with Row Level Security (RLS) enforced at the PostgreSQL level. Every table that contains tenant data carries an org_id column. All queries are filtered by org_id at the application layer AND enforced by RLS policies at the database layer. This is a hard architectural constraint — it must never be bypassed.

4. API Design

4.1 API Conventions

Base URL: https://api.yourdomain.com/v1

Protocol: REST over HTTPS. JSON request/response bodies.

Authentication: Bearer token (JWT) in the Authorization header on every request.

Tenant resolution: JWT payload contains org_id. All queries scoped to this org_id.

Pagination: Cursor-based for large lists. Query params: cursor, limit (default 20, max 100).

Error format: { error: { code: string, message: string, details?: object } }

Versioning: URL-based (/v1/). Increment for breaking changes.

6. Security Requirements

Security is non-negotiable for a financial platform. Every item in this section is a hard requirement, not optional.

6.1 Authentication & Authorisation

JWT access tokens: 15-minute expiry. Refresh tokens: 30-day expiry, stored in HttpOnly cookies.

Refresh tokens are rotated on every use (one-time use). Reuse of a consumed refresh token triggers a full session invalidation for that user.

Role-based access control (RBAC) enforced at the API layer via NestJS Guards. Frontend hides UI elements based on role but backend is the authoritative enforcement point.

Every API endpoint that accesses tenant data validates that the requested resource belongs to the authenticated user's org_id.

PostgreSQL RLS policies provide a second layer of tenant isolation at the database level.

6.2 Data Protection

All data encrypted at rest (database encryption enabled at provider level).

All data encrypted in transit — TLS 1.2 minimum, TLS 1.3 preferred. HTTP requests automatically redirected to HTTPS.

Sensitive fields (ID numbers, phone numbers) should be treated as PII. Log masking must be applied — never log full ID numbers or phone numbers.

S3 documents accessible only via pre-signed URLs with 15-minute expiry. Bucket is not publicly accessible.

6.3 Application Security

Input validation on all API endpoints using Zod schemas. Reject any request that fails validation with HTTP 400.

SQL injection prevention: Prisma parameterised queries only. Never concatenate user input into raw SQL.

XSS prevention: React's default JSX escaping + Content Security Policy headers.

CSRF protection: SameSite=Strict on session cookies + CSRF token for any state-changing form.

Rate limiting: 100 req/min per IP on auth endpoints, 1000 req/min per tenant on API endpoints (via Redis).

Helmet.js middleware for security headers on the NestJS API.

Stripe webhook signature verification on every incoming webhook.

6.4 Audit & Compliance

Immutable audit log: every CREATE, UPDATE, DELETE operation on loans, repayments, borrowers, and user accounts is logged.

Audit log records: user ID, timestamp, action type, entity type, entity ID, before state (JSON), after state (JSON), IP address.

The audit_logs table must have a database-level trigger or application-level constraint preventing UPDATE and DELETE operations.

Retain audit logs for minimum 7 years (configurable per tenant for compliance requirements).

8. Coding Standards & Conventions

8.1 General

TypeScript strict mode enabled everywhere. No use of any unless absolutely unavoidable and documented.

ESLint + Prettier enforced via pre-commit hooks (Husky + lint-staged).

All environment variables validated at startup using Zod — the app must fail fast with a clear error if a required env var is missing.

No secrets or API keys in source code or version control. Use .env files locally, environment variables in production.

All TODO comments must include a GitHub issue number: // TODO(#123): description

8.2 Backend Conventions

NestJS modules: one module per domain (BorrowersModule, LoansModule, RepaymentsModule, AuthModule, BillingModule, NotificationsModule).

DTOs for all request bodies and response shapes. Validated with class-validator + Zod.

Services contain business logic. Controllers only handle HTTP concerns (parsing input, calling service, returning response).

Database access only in service files via the Prisma service. Never write Prisma queries in controllers or resolvers.

Financial calculation functions live in packages/utils/src/finance.ts. They are pure functions with no side effects and must have 100% unit test coverage.

All monetary amounts in API responses must be in cents (integers) with a separate currencyCode field. Formatting happens on the frontend.

8.3 Frontend Conventions

Page components in app/ directory. Reusable components in components/. One component per file.

All API calls via React Query hooks defined in hooks/ directory (e.g. useLoans, useBorrower, useRepayments).

Never call fetch or axios directly in a component — always go through a hook.

Format money on display using Intl.NumberFormat with the tenant's currency code. Never format money in API calls.

All forms use React Hook Form with Zod resolver. Share Zod schemas from packages/types.

Loading states: every data-fetching component must handle loading and error states explicitly. Use skeleton components for loading.

9. Key Architectural Decisions & Hard Constraints

Decision / Constraint

Rule

Reason

Money arithmetic

Always use decimal.js. Never native JS floats.

0.1 + 0.2 = 0.30000000000000004 in JS. Financial errors are unacceptable.

Money storage

Store as integer cents in the DB (e.g. R1,500.00 = 150000).

Avoids float rounding in the database layer entirely.

Multi-tenancy

Every tenant-scoped table has org_id. RLS enforced at DB level.

Prevents cross-tenant data leaks even if app-layer bugs exist.

Repayment records

Repayments are immutable — insert only, never update or delete.

Financial audit trail must be tamper-proof.

Audit logs

Audit logs are immutable — DB trigger prevents UPDATE/DELETE.

Regulatory and dispute resolution requirement.

Loan terms

Loan terms can only be edited in DRAFT status.

Prevents retroactive changes to active loan contracts.

File serving

Documents served via pre-signed S3 URLs only (15 min expiry).

Files must never be publicly accessible or proxied through the API.

Background jobs

Overdue detection runs as a scheduled cron via BullMQ, not on request.

Loan status must update even when no user is logged in.

Soft deletes

Borrowers and loans are soft-deleted (deleted_at). Hard deletes are never permitted.

Data must be recoverable. Financial records must be retained.

Shared types

API response types and Zod schemas live in packages/types and are imported by both frontend and backend.

Single source of truth. Type mismatch between client and server is a common source of bugs.

11. Glossary

Term

Definition

Tenant / Organisation

A single lender account on the platform. All data is scoped to a tenant. Equivalent to a 'workspace' or 'company' in SaaS terminology.

Borrower

An individual who has received or applied for a loan from a tenant lender. Not a user of the LMS platform.

Loan

A single lending arrangement between a lender (tenant) and a borrower, with defined principal, interest rate, term, and repayment schedule.

Principal

The original loan amount disbursed to the borrower, before interest.

Amortisation schedule

The full table of expected repayments for a loan, broken down by period, showing how much of each payment goes to principal vs interest.

Flat rate interest

Interest calculated as a fixed % of the original principal for every period, regardless of how much has been repaid.

Reducing balance interest

Interest calculated each period on the outstanding (remaining) principal balance. Results in decreasing interest charges over time.

Arrears

When a borrower has missed one or more scheduled repayments. A loan 'in arrears' has a past-due balance.

Write-off

An administrative action marking a loan as uncollectable. The loan is closed but all historical records are retained.

org_id

The database foreign key linking every tenant-scoped record to its owning organisation. Never expose this in public-facing URLs or API responses where avoidable.

RLS

Row Level Security — a PostgreSQL feature that enforces access policies at the database row level, independent of application code.

RBAC

Role-Based Access Control — the system that determines what actions a user can perform based on their assigned role (Admin, Loan Officer, Viewer).

Pre-signed URL

A time-limited URL generated by the API that grants temporary permission to upload to or download from S3 without exposing AWS credentials.

Soft delete

Marking a record as deleted (via a deleted_at timestamp) without physically removing it from the database. The record is hidden from normal queries but retained for audit purposes.
